# 评审任务：iOS 音乐播放器「特效关闭链」连续三包真机失败——对抗评审 (96) 修法草案

你是对抗评审方。你的职责是找漏洞、找反例、找更稳的替代方案，不要客套、不要复述我方结论当共识。凡你认为证据不足以支撑的推断，直接点名。

## 一、产品与故障背景（全部为已证实事实）

- iOS 原生音乐播放器（照片墙＋歌词舞台），有四个全屏环境特效：烟花 fw、孔明灯 ln、雪 sn、风 wd。特效是叠加层：特效绘制根视图 isUserInteractionEnabled=false 整窗不接点按；自有浮层卡（祝福卡/写灯钮/推荐卡）挂在主窗的 FxOverlayHost91 上，其 hitTest 为白名单制——只把命中 UIControl 本体的点交回系统，其余整屏穿透回主窗。特效的开/关按钮在「控制台」面板里（ConsolePanel82，主窗内），点控制台外区域（dim）应关闭控制台。
- 连续三包（(93)(94)(95)）真机验收同一故障：**任一特效开启后，特效关不掉、控制台也关不掉，界面点任何地方都没反应，用户只能杀 App 重进**。(95) 录屏逐帧证据（孔明灯样本）：开灯后约 6.5 秒在 App 内的每一帧，控制台与灯笼都在，没有一帧关闭成功；其间多只大灯笼视觉上压在控制台按钮区上；用户两次退到桌面/切换器收尾。用户口头补充：四个特效全都关不掉（录屏只取样了孔明灯，其余三个无录屏样本）。

## 二、关闭链的现行设计（(95) 源码，GlobalFx87.swift）

1. 正常通路：控制台特效钮 → toggleX → start/stop → setX(on,src) → 落 `p94 fx sw fx=<代号> on=… src=…`；关闭收尾另落 `p95 fx clear fx=<代号>`。点 dim 关控制台走控制台自身 handler，两处落痕递增 ConsolePanel82.handlerTrace95。
2. (95) 新增「双路兜底」：
   - 主窗上挂了一个被动探针 UITapGestureRecognizer（tapProbe92，cancelsTouchesInView=false，delegate 恒放行）。其 shouldReceive → probeRawShould95(touch)：落原始点落痕（同秒节流）＋ arm 后首点落 `p95 probe first`。
   - **看门狗 probeGuardCheck95 的唯一调用点就在 probeRawShould95 末尾（:818）**。逻辑：特效开启期，点按若命中控制台登记的特效钮帧或 dim 帧 → 挂 350ms 计时 → 期内 handlerTrace95 无新值（handler 链断裂）→ 探针直接执行关闭（经既有 setX 通路 toggle，或发通知请控制台 dismiss），落 `p95 probe guard fired=1`。
   - arm 边沿（任一特效 false→true）必落三串：`p93 probe arm`、`p94 fx arm`、`p95 probe arm view=…`；setX 内必落 `p94 fx sw`。这些都是同步落盘的面包屑（Breadcrumbs），同系统内其他面包屑（如 deck 系列）在日志中正常出现，证明落盘机制本身在工作。

## 三、取证现状：两次真机日志都没抓到被卡会话（这是本轮评审的核心困境）

- 日志留存机制：两份轮换日志文件；新会话启动时把上一会话**最后 200 行**转存为 prevtail（preservePreviousSessionTail，启动时一次性执行、非滚动）；导出 = prevtail ＋当前文件内容。
- 第一份日志（录屏后约半小时导出）：录屏会话（2 分钟窗口）零行——被后续使用挤出 200 行尾巴；留存段内特效从未开启。刷屏源：Web 画布 resize 行约 30 条/秒。
- 第二份日志（按约定流程：开特效被卡→杀 App→重进→第一时间导出）：留存内四个衔接紧密的会话合计约 83 秒，**没有任何一段开启过特效**——fx 开关/arm/raw/dismiss/clear 全套面包屑计数全为 0，而同期 deck 等面包屑正常落痕。被卡会话不在窗口内；且 prevtail 只在下次启动时落盘，若杀 App 后启动链异常，尾巴可能断链。四会话合计仅 83 秒说明被卡会话要么发生在留存链之外，要么其面包屑根本没产生。
- 墙面高频面包屑消耗实测：快滑期约 70.5 行/秒，200 行尾巴只覆盖 2.8 秒。
- **因此点按到底死在哪一层（窗口/覆层拦截、分发、执行）至今无法定案**，判据已备好（见草案 4），缺的是样本本身。

## 四、我方 (96) 修法草案（请逐条攻击）

1. **取证三修**：
   a. fx 事件行（fx sw / arm 三串 / fx clear / dismiss try / probe 系列）进「钉住区」：不参与环形挤出，单独小文件或标记保留，保证被卡会话的 fx 事件无论刷屏多少都留得下。
   b. prevtail 由 200 行扩到 ≥2000 行，或对墙面高频行（wall.cache/pf83/cvr.stat/wall.dec78/web resize 等）做同秒合并节流（二选一或叠加）。
   c. prevtail 改滚动落盘：不再只在下次启动时 save，改为运行中周期性/关键事件时同步尾巴文件，避免被杀断链。
2. **看门狗与点按脱钩**：特效开启（arm 边沿）即以定时器武装一个独立看门狗，不依赖任何点按到达；其职责改为周期性自检「关闭通路是否活着」（具体检查什么、周期多长，我方未定案——这是请你重点设计/攻击的点）。原 350ms 点后看门狗保留作第二层。
3. **独立退出路**：在上述之外，再给一条不经过控制台 handler 链、不经过特效覆层的退出路径（候选：系统级手势/音量键/摇一摇/灵动岛或锁屏控件/强制手势区，我方未定案），保证任一特效开着时用户永远有路可退；同时维持既定硬要求：覆层只截自己的可交互元素、其余点按放行；控制台必能打开、再点特效钮当帧关闭。
4. **分流判据**（样本到位后）：arm 有、raw 无 → 死在窗口/覆层拦截层；arm＋raw 有、dismiss try 与 fx clear 无 → 死在分发/执行层；raw 有、guard fired=1 且 fx clear 无 → 看门狗执行路径本身断裂。
